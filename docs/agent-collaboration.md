# 多智能体协作与异常处理

报告沿用简历分析、岗位分析、招聘搜索、职业决策、用户确认、行动规划的主流程。职业决策现在可以请求岗位 Agent 定向补查，再依据新旧原文重新判断。

## 何时自动补查

决策结果的 `evidence_requests` 提供 `target_id`、`question`、`reason`。例如已有岗位样本未说明 Docker 是必需还是优先条件，决策 Agent 可以请求补查该方向的岗位要求。

补查使用既有 LightRAG 岗位知识库，不自动扩大到新的职业方向或实时招聘搜索。问题应只包含公开岗位要求；个人经历、技能实践、求职意愿等缺口仍交由用户回答。控制额度及补查历史会传给决策 Agent，历史记录本身不作为事实证据。

- 整份报告最多两轮，每轮最多三项；用户补充后的修订共用额度。
- 同一目标的相同问题不重复执行，忽略空白和英文大小写差异。
- 原有来源和岗位发现会保留，新来源和发现合并后再交给决策 Agent，继续执行原文引用校验。
- 同一来源编号若出现正文或来源位置冲突，本次补查不合并，保留已保存版本。
- 没有新证据或补查暂不可用时，保留未知及限制说明，不据此断言没有岗位要求或用户不符合。

## 遇到失败时

| 情况 | 处理 |
| --- | --- |
| 可选招聘搜索返回模型、检索或校验失败 | 清除未通过校验的发现与来源，保留失败状态，继续依据简历和岗位知识库分析。 |
| 岗位补查没有结果或返回失败 | 保留原有岗位证据，将执行结果交给决策 Agent，并在报告中注明限制。 |
| 补查完成后重新决策失败 | 补查结果已保存到检查点；用户重试时从重新决策继续。 |
| 简历分析、初次岗位分析、职业决策或行动规划失败 | 沿用检查点重试，提示用户处理，不生成成功报告。 |

工作流不会自动将所有异常都视为可恢复问题；输入错误、代码异常仍会使任务失败。模型请求的超时与重试继续使用原有配置。

## 查看执行依据

页面生成进度会显示补查阶段。工作流状态接口的 `collaboration` 包含轮次上限、已用轮次，以及每项请求、结果和执行指标；最终报告将相同记录保存到 `meta.provenance.collaboration`，附录列出补查问题及结果。

现有 `meta.execution` 仍按保留结果统计，不代表完整调用账单；补查调用的执行指标另外保存在上述补查记录中。

## 本地验证

运行 `python -B backend/scripts/check_report_workflow.py`，检查使用临时 SQLite 和离线 Agent，覆盖定向委派、来源合并、循环上限、补查失败降级、检查点恢复和可选搜索失败。测试验证流程和约束，真实模型是否能识别恰当的补查时机仍需用实际案例评估。
